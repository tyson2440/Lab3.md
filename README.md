### Questions

1. Does a successful NG Setup guarantee that a UE can register? Explain.

No, it doesn't. A successful NG Setup only confirms that the connection between the gNB and AMF has been established. The UE must still go through several procedures, such as synchronization, RRC connection, NAS registration, authentication, and security configuration. Therefore, the UE registration can still fail even if the NG Setup was successful.

2. Why can the UE establish an RRC connection but still fail Registration?

This is because RRC connection establishment and UE registration are two different procedures. RRC establishes communication between the UE and gNB, while registration involves communication with the 5G Core through NAS. As a result, the UE can reach the NR_RRC_CONNECTED state but still fail to register with the AMF. In my case, this happened because the AMF did not receive the authentication response from the AUSF before its timer expired. The AUSF response arrived just 1 ms after the AMF timeout.

3. What additional procedure is required after Registration before user data can be exchanged?

After successful registration, the UE needs to establish a PDU Session. This procedure provides the connection to the user plane and assigns an IP address to the UE, allowing it to exchange user data over the network.

**Questions:**

1. Why does RFsimulator use a TCP connection instead of a physical antenna?

RFsimulator uses a TCP connection to transfer simulated radio samples between the UE and gNB instead of sending signals through physical antennas. This makes it possible to test the 5G radio system without requiring real RF equipment, which can be expensive.

2. Are the TCP packets exchanged by RFsimulator the same as the UE's application-layer IP packets?

No, they are different. The TCP connection used by RFsimulator carries simulated radio IQ samples between the nrUE and gNB. These are not the same as the IP packets generated by applications running on the UE.

3. Does using RFsimulator mean that the UE and gNB are performing no physical layer processing? Explain.

No. Even when using RFsimulator, both the UE and gNB still perform the main 5G NR physical layer operations, including synchronization, OFDM processing, channel coding, modulation, and scheduling. The main difference is that radio signals are simulated instead of being transmitted through physical antennas.

**Questions:**

1. Why can the UE potentially synchronize with the gNB even when the IMSI is incorrect?

The UE can still synchronize with the gNB because this process only depends on detecting the SSB signals at the physical layer. It does not involve checking the UE's identity. Identity verification takes place later, when the network starts exchanging signaling messages.

2. Which network function is involved in UE authentication?

The main network functions responsible for authentication are the AUSF (Authentication Server Function) and UDM (Unified Data Management). They work together to verify the UE's identity and authentication information using the IMSI and secret keys stored in the UDR/MySQL database.

3. Why does changing an IMSI affect Registration but not the RFsimulator TCP connection itself?

This happens because the RFsimulator TCP connection is only responsible for transferring simulated IQ samples between the UE and gNB. The IMSI, on the other hand, is used during NAS signaling and is verified by the 5G Core Network. Therefore, changing the IMSI can cause registration to fail without affecting the underlying TCP connection.

4. What evidence proves that restoring the correct configuration solved the problem?

After changing the IMSI back to 001010000000001, the AMF successfully registered the UE. Additionally, the oaitun_ue1 interface received an IP address again, and ICMP Ping packets to 192.168.70.135 were successfully sent and received. These results confirm that restoring the correct configuration resolved the issue.

**Questions:**

1. Which parts of the 5G system remain functional when physical RF hardware is replaced with RFsimulator?

Most of the 5G protocol stack continues to operate normally. This includes PHY, MAC, RLC, PDCP, RRC, and NAS processing, as well as synchronization, random access, RRC connection establishment, UE registration, and PDU Session establishment.

2. Why is RFsimulator useful for testing the 5G protocol stack?

RFsimulator allows the gNB and nrUE to communicate without needing physical antennas or expensive RF equipment. This makes it easier to test and troubleshoot signaling procedures, protocol behavior, network configurations, and user-plane connectivity in a controlled environment.

3. Why might latency and throughput differ between RFsimulator and a real 5G deployment?

The main reason is that RFsimulator does not fully reproduce real radio conditions, such as signal fading, interference, path loss, antenna characteristics, and propagation delays. In addition, its performance can be affected by CPU usage, software processing, and Docker container workloads. Because of these differences, latency and throughput measurements may not match those of a real 5G network.

4. What would need to change if you wanted to test a physical UE instead of OAI nrUE?

The RFsimulator would need to be replaced with physical radio equipment, such as SDR hardware connected to the gNB and antennas. The physical UE would also require a valid SIM or USIM containing the appropriate subscriber information. Additionally, radio parameters such as frequency and bandwidth would need to be configured for real-world operation. Alternatively, realistic radio conditions like fading, interference, and path loss could be added to the simulation, although this would still not perfectly reproduce an actual wireless environment.
